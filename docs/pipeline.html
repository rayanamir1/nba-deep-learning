How the totals model works, stage by stage

Thirteen stages turn raw NBA data into one number per game: a calibrated probability that the final score goes over the line. Each stage below lists where its inputs come from, the algorithm, why the math holds up, and where its output goes. Click any box in the schematic to jump to its stage.

The one invariant the whole system obeys

Every feature used for a game decided at time t comes only from rows where available_at < t. Most public models break this rule without noticing, which is why their backtests look great and their live results fall apart.

02

Raw lake and point-in-time warehouse

storage · ETL
From
1 · all sources
Algorithm

Idempotent fetch jobs write raw API responses to an append-only Parquet lake and never edit them. Transform jobs build DuckDB tables from the lake. Every row carries two timestamps: event_time (when it happened) and available_at (when we could first have known it). Features are read with an as-of join on available_at < t_decision.

Why

Keeping raw data means we can rebuild any table after fixing a bug. The as-of join is how we enforce the invariant in code instead of hoping for it. Example: a box score has available_at = the final buzzer. An injury report snapshot has available_at = its publish time. A closing line has available_at = tip-off, so it can never leak into a pre-game feature.

Test

A leakage unit test. Corrupt every row with available_at ≥ t (shuffle it, add noise), rebuild the features for time t, and assert they come out byte-identical.

03

Possession and stint parser

feature · deterministic
From
2 · play-by-play table
Algorithm

A state machine walks each game's events in order. A possession ends on a made field goal (unless it's an and-one), the last free throw of a trip, a defensive rebound, a turnover, or the end of a period. In parallel it tracks the 10 players on court from period starters and substitutions. A new stint starts whenever that set of 10 changes.

possession(game, period, off_team, def_team, 5 off ids, 5 def ids, start_s, end_s, points, ended_by) stint(game, 10 player ids, possessions_each_side, points_each_side, seconds)
Why

A total is literally possessions × points per possession, so we need possessions counted exactly. The box-score formula misses by 1.8 to 6.3 possessions per game. That is 2 to 6% of pace, which is bigger than the edge we're hunting. Stints are also the rows RAPM regresses on (stage 5).

Test

For every game, points summed over possessions must equal the final score, and seconds summed over stints must equal the game length.

04

Shrunk player skill estimates

feature · empirical Bayes
From
2 · box scores, tracking3 · per-possession counts
Algorithm

For each player and each stat, decide its "true talent as of date t" the way DARKO does. Weight every past game by how recent it is, then shrink toward a prior for the player's role.

w_i = λ^(days_since_game_i) # 0 < λ < 1, tuned per stat M = Σ w_i · makes_i A = Σ w_i · attempts_i p̂ = (M + α) / (A + α + β) # Beta(α, β) prior fit to the league, by role

For counting rates (turnovers, offensive rebounds, free-throw attempts per possession) we use the Gamma-Poisson version of the same idea.

Why the math holds

A Beta prior plus binomial makes and misses gives a Beta posterior, and the formula above is its mean. Shrinkage is just the optimal estimate given noise. A player shooting 40% from three on 100 attempts has a sampling standard deviation of √(0.4·0.6/100) ≈ 4.9 points. Most of a "hot streak" is noise, and this formula discounts it automatically. The decay λ is picked by minimizing log loss on the next game, so it is fitted, not guessed.

05

Player impact: RAPM with a box prior, for offense, defense and pace

feature · ridge regression
From
3 · stint rows4 · skills → prior
Algorithm

One row per stint. The design matrix has an offense column and a defense column for every player: +1 if the player is on the court on that side. We solve a ridge regression pulled toward a prior instead of toward zero, which is how EPM and LEBRON work.

y_s = 100 · points_s / possessions_s # stint offensive rating β̂ = argmin Σ_s r_s·poss_s·(y_s − x_sᵀβ)² + κ·‖β − β_prior‖² = β_prior + (XᵀWX + κI)⁻¹ XᵀW (y − Xβ_prior) β_prior = SPM(skills from stage 4) # linear model: skills → long-run RAPM r_s = recency weight, W = diag(r_s · poss_s)

We also fit a third model with the same X, where y_s = possessions per 48 minutes in that stint. That gives each player a pace rating. Most public systems don't publish one, and it is the direct input a totals model needs.

Why the math holds

Players who always share the court (a starting five) make the columns of X nearly collinear, so ordinary least squares returns huge, unstable numbers. Ridge is the same as putting a Gaussian prior N(β_prior, σ²/κ) on each rating and taking the most likely value. With little data a player sits near their box-score prior, and with lots of data the on-court results take over. Weighting by possessions makes long stints count more than 20-second ones.

Cadence

Refit nightly using only stints before that date. In backtests, refit for each simulated date, using a cache keyed by date.

06

Referee crew effects

feature · mixed-effects model
From
2 · crew per game3 · FTA and possessions per game
Algorithm

A model with random effects for each referee, fit on free-throw attempts per possession and on pace, controlling for the two teams.

FTr_g = μ + team_home + team_away + Σ_{ref ∈ crew_g} u_ref + ε u_ref ~ N(0, τ²) # shrinkage toward 0 is learned from the data
Why the math holds

A referee works about 60 to 70 games a season, crews rotate, and team styles get mixed in. A raw "this ref's games average 228" number is mostly noise. Random effects shrink each referee toward average in proportion to how much data we have, the same idea as stage 4. Expect a small effect, and we keep it only if stage 13 says it helps.

07

Schedule context: rest, travel, altitude

feature · deterministic
From
2 · schedule1 · arena table
Algorithm

Pure functions of the schedule: days of rest, back-to-back, 3 games in 4 nights, km traveled since the last game (haversine distance between arenas), time-zone shift, altitude of the venue, home or away, and week of the season.

d = 2R · asin( √( sin²(Δφ/2) + cos φ₁ · cos φ₂ · sin²(Δλ/2) ) ) # R = 6371 km
Why

FiveThirtyEight found rest worth about 46 Elo points and modeled travel and altitude separately. The early-season study found week-1 unders hit 58.2%, so week of season goes in as a feature. These are cheap, exact and known far in advance.

08

Availability and minutes projector

projection · logistic + gradient boosting
From
2 · injury snapshots as of t4 · decayed minutes7 · rest
Algorithm

Two steps. First, the probability each player plays, given their latest report status, from a logistic regression on historical status → played outcomes. Second, minutes given that they play, from a LightGBM regressor (recent minutes, starter flag, rest, teammates out, spread as a blowout proxy). Then renormalize so each team's expected minutes sum to 240.

P(play_p) = σ(a_status + b·x_p) E[min_p] = P(play_p) · ĝ(x_p) # ĝ = gradient-boosted minutes model scale so Σ_p E[min_p] = 240 per team # 5 players × 48 minutes
Why

Who plays moves a total more than anything else, and it is where the market is slowest (late scratches). This is the job of RAPTOR's depth-chart algorithm and of Voulgaris's "Van Gundy" model. Gradient boosting fits the nonlinear parts (a starter's minutes collapse when the game is a blowout), and the renormalization keeps the minutes physically possible.

Watch out
Leakage trapNever mark a player "out" because the box score shows 0 minutes. That uses the result. Availability comes only from the injury report snapshot taken before t.

09

Game projection: pace × points per possession

projection · Poisson GLM + additive ratings
From
5 · O_p, D_p, π_p6 · referee effects7 · context8 · minutes3 · actual possessions (training target)
Algorithm

Weight every player's rating by their share of the game, w_p = E[min_p] / 48, so the five on-court slots sum to 5.

log E[poss] = c₀ + Σ_{p∈A∪B} w_p·π_p + γᵀ·context + u_ref_pace # Poisson GLM ORtg_A = L + Σ_{p∈A} w_p·O_p − Σ_{q∈B} w_q·D_q + h_home + δᵀ·context + u_ref_FT ORtg_B = same, with the teams swapped μ = E[poss] · (ORtg_A + ORtg_B) / 100 # projected total
Why the math holds

Pace is a count, so we fit it with a Poisson model on the log scale. Two fast teams compound multiplicatively instead of adding. Efficiency is additive in player ratings because that is exactly how RAPM was fit in stage 5, so we're using the ratings on the same scale they were learned on. The total then follows from the definition: possessions times points per possession.

10

Distribution of the total

probability · heteroscedastic normal, later simulation
From
9 · μ, E[poss], projected margin
Algorithm

Version 1 treats the total as normal with a mean from stage 9 and a standard deviation that depends on the game. A second small model predicts σ from pace and projected margin, since blowouts empty the benches and close games bring late fouling and overtime.

T ~ Normal(μ, σ_g²) P(over L) = 1 − Φ( (L + 0.5 − μ) / σ_g ) # L + 0.5 handles a push on whole-number lines baseline σ: closing totals miss by MAE ≈ 13.8 pts, and for a normal MAE = σ·√(2/π) ⇒ σ ≈ 13.8 / 0.798 ≈ 17.3 pts

Version 2 is a possession-by-possession Monte Carlo simulation like Voulgaris's Ewing. It captures fat tails and overtime (an extra ~20 points in roughly 6% of games), which a normal curve misses.

Why

The bet is on a line, not a point estimate. A 2-point edge means very different things when σ is 14 versus 20, and the probability is what stage 12 needs to size the bet.

11

Calibration and market blend

probability · isotonic regression + shrinkage
From
10 · raw P(over), μ2 · current line as of t13 · out-of-fold history
Algorithm

First, shrink the model's mean toward the market's number, with a weight k learned walk-forward. Then fit an isotonic calibration map on past out-of-fold predictions, so that "60%" really means 60%.

μ_final = L_market + k · (μ_model − L_market) # k ∈ [0, 1], fit walk-forward p_cal = isotonic( P(over L | μ_final, σ_g) )
Why the math holds

The market is efficient, so most of the gap between our number and the line is our own error. k measures how much of that gap is real signal: k = 0 means the model adds nothing, and k = 0.3 means 30% of our disagreement holds up. That is the most honest single number in the project. Walsh and Joshi found that choosing models by calibration returned +34.7% where choosing by accuracy returned −35.2%. Isotonic regression is used because it only assumes the map is monotone, nothing about its shape.

12

Bet decision and sizing

decision · expected value + fractional Kelly
From
11 · p_cal2 · price on offer as of t
Algorithm
break-even at −110: p_be = 110 / 210 = 0.5238 edge = p_cal − p_be ; bet only if edge > τ # τ tuned in stage 13 Kelly: f* = (b·p − q) / b, b = 100/110 = 0.909, q = 1 − p example p = 0.55 → f* = (0.909·0.55 − 0.45) / 0.909 ≈ 5.5% → stake ¼ Kelly ≈ 1.4% of bankroll

Every bet is logged with the line and price taken and the timestamp, so stage 13 can compare it with the close.

Why

Full Kelly maximizes long-run growth only if p is exactly right. Ours is estimated, so we take a quarter of it, which gives up a little growth for much smaller drawdowns.

13

Walk-forward evaluation

evaluation · the backtest harness
From
12 · bet log11 · every prediction2 · closing lines, final scores
Algorithm

An expanding-window replay. For each date d in the test seasons, set the clock to the decision time, run stages 3 to 12 using only data available then, record predictions and bets, then step to d + 1. Never use random K-fold, which shuffles the future into training.

metrics per season and overall: MAE(μ_final, final total) vs MAE(closing line, final total) Brier, log loss of p_cal vs the market's no-vig probability calibration: reliability curve, expected calibration error CLV = signed(close − line taken) in points, averaged over bets ROI with a 95% bootstrap confidence interval, plus number of bets sample size: SE of win rate = √(p(1−p)/n); at n = 1000, p = 0.55 → 1.6 pts so 55% vs 52.4% is only about 1.7 standard errors apart
Why

This is what kept the best models honest (EPM publishes live MAE separately from its backtest MAE). Closing line value settles much faster than win rate, so it's our early warning. New features go in one family at a time and stay only if they improve out-of-sample numbers.

Where deep learning fits

We'll have about 1,230 games a season, so roughly 15,000 games from 2013-14 on. That's small for a neural net trained on game rows, and on tabular data like this, structured models and gradient boosting usually win. Deep learning earns its place one level down, where the data is large: millions of possessions and tracking frames. A sequence model over possessions (for example, a transformer predicting points per possession from the 10 players and game state) can become a new feature for stage 9 or the engine for the stage 10 simulation. It goes in the same way as everything else, only if stage 13 says it beats what's there.

Open questions before we build

There are no gaps between the stages, but three inputs depend on choices only you can make.

  1. Historical odds source. Stages 11 to 13 need opening and closing totals for every past game. Free options are community archives (closing lines only, quality varies, they mostly stop around 2022-23). Paid options are services like The Odds API, which has historical snapshots from about mid-2020 plus live lines. Is a paid data budget OK?
  2. When do you place bets? This sets the decision time t, which decides which injury reports and referee crews exist yet, and which line we compare against. Night before, morning of, or about an hour before tip-off?
  3. Which seasons? I'd start at 2013-14, when tracking data begins, and hold out the last two seasons as the true test that we look at as rarely as possible.
